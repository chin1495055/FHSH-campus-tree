# 協作新手備忘

> 供 Saori 與 Qmoa 共同協作參考。
> 兩位夥伴依專長與認領項目分工；產品方向、技術方案與協作流程透過討論共同確認。

## 先搞懂幾個詞

| 詞 | 白話解釋 |
|---|---|
| repo（儲存庫） | 一個專案的資料夾，加上它所有的修改歷史 |
| 本地（local） | 你電腦上的那一份 |
| 遠端（remote）／`origin` | GitHub 上那一份，大家共用 |
| commit | 存檔點。把目前的改動存起來，附一段說明。**只存在你電腦，別人還看不到** |
| push | 把你的 commit 推上 GitHub，別人才看得到 |
| pull | 把 GitHub 上別人的新 commit 拉到你電腦 |
| `main` | 主線，大家共用的正式版本 |
| branch（分支） | 從主線分出去的支線，在上面改不會影響主線 |
| PR（Pull Request） | 「請把我分支上的改動合併到主線」的請求，讓別人先看過再合併 |
| merge（合併） | 把分支的改動併進另一條線 |
| conflict（衝突） | 兩個人改了同一個地方，git 不知道要留誰的，要人來決定 |

## 每天的固定流程

### 1. 開工前：先拉最新版

```bash
git pull
```

**一定要先做。** 不然你會在舊版本上改，之後合併很麻煩。

### 2. 改完之後：看一下改了什麼

```bash
git status
```

會列出哪些檔案被改了、哪些是新檔案。確認沒有不該放進去的東西（見下面「不要 commit 的東西」）。

### 3. 存檔：commit

```bash
git add 檔案名稱
```

```bash
git commit -m "用一句話說明改了什麼"
```

- `git add` 是挑出要存的檔案，`git commit` 才是真的存檔。
- 盡量一個 commit 只做一件事，例如「新增神獸頁文案」，不要把不相關的改動混在一起。
- 說明要寫「改了什麼」，不要寫「更新」「修改」這種看不出內容的字。

### 4. 上傳：push

```bash
git push
```

push 之前最好再 `git pull` 一次，確認這段時間隊友沒有推新東西。

## 出狀況時

### push 被拒絕（rejected）

看到 `rejected`、`non-fast-forward`、`fetch first` 這類字，意思是**別人先推了新東西，你的版本落後了**。

處理方法：先 `git pull`，再 `git push`。

**千萬不要用 `git push --force`**（或 `-f`）。它會用你的版本強制蓋掉 GitHub 上的版本，隊友已推上去的改動可能因此消失。

### 發生衝突（conflict）

`git pull` 之後看到 `CONFLICT`，代表你和別人改了同一個檔案的同一段。

- **不用緊張**，東西沒有壞，只是 git 在等人決定要留哪個版本。
- 檔案裡會出現這種標記：

  ```
  <<<<<<< HEAD
  你的版本
  =======
  別人的版本
  >>>>>>> ...
  ```

- 不確定怎麼選的話，**先和另一位夥伴討論，或請 Claude 協助**，不要隨便刪。

### 怕把東西弄壞

- 還沒 commit 的改動，在 `git status` 看得到，可以先停手問人。
- 已經 commit 但還沒 push 的，都只在你電腦上，還來得及改。
- **已經 push 上去的就不要自行修改歷史**，先和另一位夥伴討論處理方式。

### 中文檔名變成一串亂碼

`git status` 顯示中文檔名被轉成代碼（例如 `資料夾/檔名`），是 git 的顯示方式，檔案本身沒壞。想看到中文的話，執行一次：

```bash
git config --global core.quotepath false
```

## 不要 commit 的東西

- **密碼、API 金鑰、token、`.env` 檔**：推上 GitHub 等於公開。就算之後刪掉，歷史紀錄裡還是找得到。
- **真實個資**：比賽規則禁止。模擬資料的人名、電話要明顯是假的。
- **很大的檔案**：影片、原始大型資料檔會讓 repo 變得很肥，每個人 clone 都很慢。
- **自動產生的東西**：`node_modules/`、`.DS_Store`（Mac 自動產生的檔案）。這些應該列進 `.gitignore`（告訴 git 忽略哪些檔案的清單），由團隊一起確認設定。

## 寫程式時：開自己的分支（10/23 定案）

寫 App 的程式時，**不直接在 `main` 上改**。每個人開自己的分支，做完一個功能再自己合回 `main`，不用等對方 review。

分支就像自己的草稿本：在上面怎麼改都不會影響 `main`，也不會弄壞對方正在用的版本。

### 1. 開分支

先確定在 `main`、而且是最新版：

```bash
git switch main
```

```bash
git pull
```

開一條自己的分支，名字是「自己的名字/在做什麼」：

```bash
git switch -c qmoa/notices
```

### 2. 在分支上照平常的方式 commit

和上面「每天的固定流程」一樣，改一小塊就 commit。想備份到 GitHub 可以 push 分支（第一次要加 `-u`）：

```bash
git push -u origin qmoa/notices
```

### 3. 做完一個功能：合回 main

先把 `main` 上對方的新東西拉進自己的分支。**有衝突就在這一步、在自己的分支上解決**，不會弄壞 `main`：

```bash
git pull origin main
```

打開 App 確認還能正常操作，再切回 `main` 合併、push：

```bash
git switch main
```

```bash
git pull
```

```bash
git merge qmoa/notices
```

```bash
git push
```

push 之後 Discord 會自動收到通知，對方就知道要 pull。

### 4. 繼續做下一個功能

回到第 1 步，開一條新分支（例如 `qmoa/share`）。用完的分支可以刪掉：

```bash
git branch -d qmoa/notices
```

`-d` 只會刪掉已經合併的分支，還沒合併的會被擋下來，不用怕刪錯。

## 黑客松當天（10/24）特別注意

- **開工前先說好誰改哪個檔案**，盡量不要兩個人同時改同一個檔案。
- **小步快跑**：改好一小塊就 commit、push，不要累積一整個早上才推。
- **不要把會壞掉的東西推上主線**：團隊可能隨時在部署。不確定能不能動，先和另一位夥伴確認。
- **14:00 定版**：之後只修 bug，接著錄影片、上傳 YouTube。15:00 前要通過審核才能抽現場 Demo，16:00 是最後期限。
- **PWA 快取**：部署後如果看到的還是舊畫面，可能是瀏覽器快取了舊版。先試試重新整理，或用無痕視窗打開。

## 用 Claude 幫忙

不確定的時候，直接跟 Claude 說你想做什麼，例如「幫我把改動推上去」「pull 出現衝突了」。Claude 會解釋每一步在做什麼。

**Claude 也會出錯。** 它要執行 `--force`、`reset --hard`、刪除檔案這類不能復原的指令時，先停下來問清楚。

## 不想打指令的話

可以用 [GitHub Desktop](https://desktop.github.com/)，它是圖形介面，pull、commit、push 都是按鈕。概念和上面完全一樣。
