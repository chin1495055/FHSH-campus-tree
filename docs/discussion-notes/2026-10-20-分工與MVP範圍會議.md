### 3. 開發範圍的原則

- 規則寫「Day 1 起可開始討論與寫程式」，Day 1 是週五晚上。不確定主辦單位會多嚴格，Day 1 可能會公布特別的規則。
- 如果嚴格執行，當天的開發時間只有大約 6 小時。
- 主辦要的是 **MVP**，用來收集點子，不是完整產品。所以**主打兩三個重點功能**，有時間再加。
- 做法：Saori 先從 User Stories 寫 PRD，再從 PRD 挑要主打的功能。

### 4. 使用者角色

- **優先服務兩種角色：在地守護者、遠端關注者。**
- 市府／維護人員不做。大家應該都會從市府的角度出發，我們做市民端比較有趣，也比較符合活動想要的活潑、創新調性。
- 親子同行者這次不做。

### 5. 每個 User Story 的取捨

| User Story | 決定 |
|---|---|
| US-01 找附近的樹 | **做**。打開就看到地圖和樹木標記；地圖上顯示開放資料的樹。**不做真正的定位**，固定以競選總部為中心（假定位）。「拒絕定位權限」的情境不做 |
| US-02 單棵樹的資料 | **做**。用一個固定的假連結開到某一棵樹（Demo 用）；樹的資料、資料不齊全的情況都用假資料 |
| US-02a 大樹神獸 | **做**。Demo 那一頁就放神獸；做幾頁假資料，就放幾隻神獸 |
| US-03 在地守護／遠端關注 | **做**。兩種的差別見下方；在地守護的現場驗證先做假的，直接通過 |
| US-04 掃 QR code | **做**。用開放資料的樹木資料產生 QR code，掃了打開那棵樹 |
| US-05 現場回報 | **做**。上傳照片（Saori 做過，不難）和勾選觀察項目 |
| Epic C（US-06 異動公告、US-07 異動提醒、US-08 分享卡） | **這次不做**，P0 已經夠多 |
| 圖鑑（原 US-09） | **改成要做**，放在在地守護者的功能裡。像 Pokémon GO 那樣收集，看自己收集了哪幾隻 |
| 社區佈告欄（新增） | **要做**，見下方 |

選定的 P0 驗收條件大約 12 個功能。這裡的「功能」指的是軟體功能，不是頁面。

### 6. 在地守護和遠端關注的差別

- **在地守護**：住家附近（方圓幾公里）的樹。**主動**角色，可以每天觀察樹況、回報。
- **遠端關注**：**被動**角色，像「訂閱」這棵樹，被動收到這棵樹最近的狀況。動機是對某個樹種有興趣，或在乎某棵樹。

### 7. 社區佈告欄（新功能）

- 沒辦法真的在樹上貼一張紙，所以在 App 裡做一個「樹的佈告欄」。
- **在地守護者可以貼活動**，例如在樹下揪野餐、小型聚會。
- **遠端關注者會收到活動訊息**，自己決定要不要參加；在地的人當然也能參加。
- 為什麼只讓在地的人貼：重點是在地社區，遠端的人特地跑去發起活動不太合理。
- 目的：守護樹的同時，也讓社區更緊密。守護人數的數字也可以用介面呈現出「社區」的感覺。

### 8. 遊戲化做到哪裡

- 時間不夠做對戰。這次做到：**地圖上點樹 → 出現神獸和資料 → 收集圖鑑**。
- 更完整的遊戲化（玩法回饋、3D 建模）要有新夥伴加入才做得到。

### 9. 找夥伴

- Day 1（週五）晚上再找人。
- 如果有人加入，就分工各做各的功能，最後一起 push、合併到 GitHub。
- 寫交接文件可能找不到人就白做了，所以**先做簡單版 MVP，真的有人加入再說**。

### 10. 品牌與設計

- Qmoa 介紹了品牌方向：廟紅（溫暖）、路樹綠（守護）、廟金（信仰），以大樹公的守護意象為核心。
- 這是團隊內部對焦用的，Demo 時不一定有時間講。
- 最重要的主軸是**好玩、大家能參與、社區連結**。親子的部分要再改。

### 11. 協作方式

- **不用開 PR，直接 push 到 `main`**。只有兩個人，討論過就直接上，不需要互相審核程式碼。
- Saori 設定了 GitHub 接 Discord：每次 push 會自動通知，所以 commit 說明要寫清楚。
